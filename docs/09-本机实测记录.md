## 3. GRAPH 自动生成（核心成果）

### 3.1 能力探测：`CreateFB(GRAPH)` 被拒绝

```powershell
$plc.BlockGroup.Blocks.CreateFB('Graph_Sequencer_probe', $false, 2,
    [Siemens.Engineering.SW.Blocks.ProgrammingLanguage]::GRAPH)
```

**结果**：

```
The action "Create block" only supports the programming language 'ProDiag'
```

**结论**：`ProgrammingLanguage` 枚举里有 `GRAPH`，但 `CreateFB` 实际只支持 `ProDiag`。
GRAPH **只能**通过 XML 导入生成。

### 3.2 取得权威模板

把本机教程资料里的真实 V20 GRAPH 工程**复制**后只读打开、编译、导出：

| 参考工程 | 导出的 GRAPH 块 | 导出文件大小 |
| --- | --- | --- |
| `GRAPH课程9 GRAPH编写交通灯程序1_V20` | `GRAPH事件` | 68,315 B |
| `西门子GRAPH语言 钻孔系统控制_V20` | `钻孔系统自动程序` | 83,834 B |
| `西门子GRAPH语言 自动分拣系统_V20` | （导出确认无分支） | 206,738 B |
| `graph测试.ap20` | （导出确认无分支） | 72,604 B |

> 未编译的块无法导出（*"Inconsistent blocks … cannot be exported"*），
> 所以导出前必须先编译一次。
> 导出目标已存在时 TIA 会拒绝，必须先删同名文件。

**发现**：这些教程 GRAPH 块**都没有分支**（钻孔子程序的 `Branches` 为空、
交通灯只有 `SimBegin` 形态、自动分拣/ graph测试 无分支）。
→ 分支拓扑规则只能靠导入报错逐条实测（见 3.4）。

### 3.4 分支拓扑：实测出的合法写法

**被 TIA 拒绝的写法（报错原文）：**

| 写法 | 报错 |
| --- | --- |
| `步 → AltEnd` | `A connection between "Step3" and "Branch 2" cannot be created` |
| `转换 → AltBegin` | `A connection between "Trans2" and "Branch 1" cannot be created` |
| `转换 → SimEnd` | `A connection between "Trans7" and "Branch 4" cannot be created` |

**被 TIA 接受的写法**（选择分支转换在分支内、并行分支转换在分支外）见
[04 文档第 5 节](04-GRAPH操作指南.md#5-分支拓扑规则全部经-tia-v20-导入实测)。

**结论**：这些约束在 `SW.PlcBlocks.Graph_v5.xsd` 里**完全没有表达**
（`BranchRef` 只声明了两个可选 int 属性）。
→ 必须靠"导出真样本 + 导入实测报错"来发现。

### 3.5 其它实测确认的 GRAPH 约束

| 约束 | 证据 |
| --- | --- |
| `<Graph>` 必须带 `xmlns` | 缺了报 `Attribute 'xmlns' … mandatory in 'Graph'` |
| 内层 `<FlgNet>` 不带 `xmlns` | 带了报 `…FlgNet/v5 中的 "FlgNet" 无效` |
| GRAPH 块**不写** `<MemoryLayout>` | 写了报 `Missing XML attribute 'ReadOnly' …` |
| 每个网络至少 1 元件 + 1 Wire | 空网络报 `"Wires" 的内容不完整。应为 "Wire"` |
| 每步必须有 `Supervisions` 和 `Interlocks` | 缺了报 `"Step" 的内容不完整。应为 "Supervisions"` |
| 收尾线圈是 `TrCoil`/`IlCoil`/`SvCoil` | 用 `Coil` 报"需要线圈/分配"；猜 `graphCoil` 报 `instruction not found` |
| 动作表行尾要换行、表尾要空 `<Action />` | 否则报 `All lines in the action table … must end with a line break` |
| 闭环回跳用 `Jump` | 用 `Direct` 报 `the sequencer does not start with a step` |
| 背景 DB 的 `Instance Scope` 用 `GlobalVariable` | 用 `LocalVariable` 编译 1 Error |

## 5. SCL 外部源

已验证的 SCL 样本（本机导入 + 生成块 + 编译通过）：

| 文件 | 行数 | 内容 | 编译结果 |
| --- | --- | --- | --- |
| `SelfHoldRelay.scl` | 14 | 最小自锁回路 | ✅ Errors=0（1 条无文本告警） |
| `MotorSequenceTON.scl` | 33 | 三电机顺序启停（4 个 TON） | ✅ Success 0/0 |

**未通过的样本**：另有一个 87 行的复杂样本
（`R_TRIG` + `TON_TIME` + 运行/停止状态机，**带中文注释**），
`GenerateBlocksFromSource()` 成功，但编译报 **7 个错误**，
且 `CompilerResultMessage.Description` 为空、拿不到错误文本。
因为无法定位也无法保证正确性，**没有收录进本仓库**。

**可能的原因**（Siemens 官方文档补充）：

> "从源文件生成块"**只支持 ASCII**；
> 若源文件含特殊字符，**必须使用 UTF-8 with BOM**。

本仓库通过的两个样本恰好都是**纯 ASCII**（无中文注释），
而未通过的那个**含中文注释**。这与官方约束吻合，
但该样本可能同时还有别的问题，**没有单独定位到根因**，故如实标注为"原因未完全确认"。

> 经验一：**SCL 的编译错误在 Openness 侧可能完全拿不到文本。**
> 这种情况下只能把源码贴进 TIA 界面编译一次看真实报错。
>
> 经验二：**先用小样本验证环境、再上复杂代码。**
>
> 经验三：**SCL 里尽量避免非 ASCII 字符**；非要用就存成 UTF-8 with BOM。

对应的 Openness 调用序列（实测）：

```powershell
$plc.ExternalSourceGroup.ExternalSources.CreateFromFile($name, $path)
$src.GenerateBlocksFromSource()
$plc.GetService<ICompilable>().Compile()
$project.Save()
```

**文件编码实测**：两个样本都是**无 BOM 的 UTF-8**；
`SelfHoldRelay.scl` 为 CRLF，`MotorSequenceTON.scl` 为 LF
—— **两种行尾都能被接受**。

## 6. 工具集自测（本次整理仓库时新增）

整理本仓库时，用新建的 7 个脚本跑了一次端到端验证，**发现了 4 个真实问题**，
全部已修复并记录在 [07 报错速查表](07-错误速查表.md)：

| # | 问题 | 现象 | 修复 |
| --- | --- | --- | --- |
| 1 | **`.ps1` 缺 UTF-8 BOM** | 脚本在 `pwsh`（PS7）下正常，交给 PS 5.1 后整份文件解析失败，报一堆 `Unexpected token` / `hash literal was incomplete` | 所有 `.ps1` 重新以 **UTF-8 with BOM** 保存 |
| 2 | `Set-StrictMode -Version 2.0` + 动态属性探测 | 遍历注册表时访问不存在的属性 → `PropertyNotFoundException`，脚本在第一步就挂 | 改用 `-Version 1.0`，且取值前先检查 `PSObject.Properties.Name` |

| 4 | `PlcTag.Comment = '…'` | `'Comment' is a ReadOnly property` | 改用 `SetAttribute('Comment', …)` |

> 第 1 条尤其值得注意：**同一个脚本在 PowerShell 7 下完全正常，
> 在 PowerShell 5.1 下却因为非 ASCII 字符被误读而彻底解析失败**。
> 这是所有"给 Openness 用的 PowerShell 脚本"都会遇到、但很少有人写下来的坑。

#### ⭐ GRAPH 拓扑往返一致性（最重要的一条）

把**输入**的 GRAPH XML 与**从 TIA 反导出**的 GRAPH XML 逐项计数比对：

```powershell
function Get-GraphTopology($p) {
    $text = [IO.File]::ReadAllText($p, [Text.UTF8Encoding]::new($false))
    $doc = New-Object System.Xml.XmlDocument
    $doc.LoadXml($text)
    $ns = New-Object System.Xml.XmlNamespaceManager -ArgumentList $doc.NameTable
    $ns.AddNamespace('g','http://www.siemens.com/automation/Openness/SW/NetworkSource/Graph/v5')
    [ordered]@{
        Steps      = $doc.SelectNodes('//g:Step', $ns).Count
        Transitions= $doc.SelectNodes('//g:Transition', $ns).Count
        Connections= $doc.SelectNodes('//g:Connection', $ns).Count
        Branches   = $doc.SelectNodes('//g:Branch', $ns).Count
        TrCoil     = $doc.SelectNodes('//g:Part[@Name="TrCoil"]', $ns).Count
        IlCoil     = $doc.SelectNodes('//g:Part[@Name="IlCoil"]', $ns).Count
        SvCoil     = $doc.SelectNodes('//g:Part[@Name="SvCoil"]', $ns).Count
    }
}
```

**实测输出**：

```
源  : {"Steps":10,"Transitions":10,"Connections":26,"Branches":4,"TrCoil":10,"IlCoil":10,"SvCoil":10}
导出: {"Steps":10,"Transitions":10,"Connections":26,"Branches":4,"TrCoil":10,"IlCoil":10,"SvCoil":10}
```

**逐项完全一致 ✅**

> 这条证据的含义：我们**手写生成的 GRAPH XML** 被 TIA V20 完整、正确地理解，
> 并且能够**原样反导出**。步、转换、连接、两种分支、三种 GRAPH 专用线圈
> 一个不少、一个不多。这是"GRAPH 自动生成真的可行"的硬证据。

#### 另外发现的两条运行层问题

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 5 | 反导出时抛 `Inconsistent blocks and PLC data types (UDT) cannot be exported.` | 有编译错误的块 `IsConsistent=false`，无法导出；原先会让整个步骤中断 | 已改为**跳过不一致的块并继续**，导出失败也不影响已成功的导入（`Skipped` 字段会记录） |
| 6 | `GenerateBlocksFromSource()` 的返回值在 PowerShell 里枚举不到内容 | 返回 `IList<IEngineeringObject>`，PS 侧拿到空集合 | 已改为**回读 `BlockGroup.Blocks` 与导入前快照做 diff** 来报告新生成的块（现在能正确打印 `AiSelfHoldTest`、`MotorSequenceTON`） |
| 7 | 连续跑 7 个 TIA 会话后，最后一次 `new TiaPortal(...)` 报 `Connection to TiaPortal failed` | 短时间内反复启停无界面 TIA 实例的资源压力 | 脚本的 `Dispose()` 是有效的（运行后无残留进程）；实务上**避免高频连续起停**，尽量在同一个会话里连续做完多件事 |
| 8 | `Get-Content -Raw` 读取**无 BOM 的 UTF-8** XML 时把 `<` 读成了 `?`，导致 XML 解析失败 | PS 5.1 的 `Get-Content` 对无 BOM 文件按 ANSI 解码，多字节字符被破坏后吞掉了相邻字符 | 读文件统一用 `[IO.File]::ReadAllText($p, [Text.UTF8Encoding]::new($false))` |

> 第 8 条与第 6 节的第 1 条是**同一个根因的两面**：
> PowerShell 5.1 对无 BOM 的 UTF-8 按 ANSI 处理——
> **写** .ps1 必须带 BOM，**读**无 BOM 的 XML 必须显式指定 UTF-8。

## 10. 网络受限环境下推送本仓库（本机实测）

本机对 GitHub 的访问是**间歇性被阻断**的，实测现象：

```
Resolve-DnsName github.com   → 140.82.114.3        （DNS 正常）
Test-NetConnection github.com -Port 443 → False     （TCP 被阻断）
```

但**并不是所有 GitHub 边缘 IP 都不通**，实测：

| IP | 443 |
| --- | --- |
| `140.82.112.3` | ✅ 通 |
| `140.82.113.3` | ✅ 通 |
| `140.82.116.3` | ✅ 通 |
| `20.205.243.166` | ✅ 通 |
| `140.82.114.3`（DNS 返回的那个） | ❌ 不通 |
| `140.82.121.3` | ❌ 不通 |

`api.github.com` / `codeload.github.com` / `ssh.github.com:443` 也都通。

### 解决办法：把 git 钉到可用的 IP

git ≥ 2.31 支持 `http.curloptResolve`（对应 curl 的 `CURLOPT_RESOLVE`），
**不需要改 hosts、不需要管理员权限**：

```powershell
git -c http.curloptResolve="github.com:443:140.82.112.3" push -u origin main
git -c http.curloptResolve="github.com:443:140.82.112.3" ls-remote origin
```

> TLS 的 SNI 仍然发 `github.com`，所以证书校验正常；
> 只是把域名解析结果换成指定的 IP。

也可以只对这一个仓库生效：

```powershell
git config http.curloptResolve "github.com:443:140.82.112.3"
```

### 其它已验证的替代通道

- `codeload.github.com` 可用 → 下载源码包不受影响
  （本机 `raw.githubusercontent.com` 与默认 git 协议被重置，但 codeload 正常）

**结论**：遇到 `Failed to connect to github.com:443` 时，
先 `Test-NetConnection` 试几个边缘 IP，再用 `http.curloptResolve` 指定一个通的即可，
**不必放弃推送**。
